# LawEverything

**조달청 실무자를 위한 법령 즉시검색 + 원문 열람 (내부망/오프라인)**

법령정보센터에서 조문 PDF를 내려받아 뒤지는 대신, 조달 법령군을 **즉시 검색**하고
**원문을 바로 읽으며**, 본문 속 인용을 클릭해 근거 조문으로 **점프**하는 도구.

검색과 원문이 본체이고, 관계 그래프는 원문을 읽다 맥락을 잡기 위한 **보조**입니다.

```
검색  →  "7조 보증금"
결과  →  공사계약일반조건 제7조 (계약보증금)
원문  →  "…계약보증금을 시행령 제50조 및 제52조에 정한 바에 따라 추가로 납부…"
           └─ 클릭 ─→ 국가계약법 시행령 제50조 (계약보증금)
```

**키보드만으로**: 입력 → `↑` `↓` → `Enter` 원문 → `Esc` 복귀. `/` 또는 `Ctrl+K`로 언제든 검색.

> **현황**: 조달 핵심 30종(법령 13 + 계약예규 17) 실수집 완료 — **1,223조문 · 노드 1,354 · 엣지 3,403**.
> 데이터는 법제처 국가법령정보 오픈API 원문입니다. (`data/procurement-laws.json`은 키가 없을 때 쓰는 축약 샘플)

## 왜 이 구조인가 — 내부망(폐쇄망) 전제

조달청 실무는 폐쇄망에서 돌아가 실시간 API 호출이 불가능하다. 그래서 **관계 계산과 데이터 수집을 분리**한다.

```
┌── 온라인 빌드 단계 (인터넷 PC) ─────────────────┐        ┌── 내부망 런타임 ──────────┐
│  법제처 오픈API로 조달 법령군 수집 (seed 기준)     │  반입   │  web/index.html            │
│  → 규칙기반 관계추출(AI 없음) → 정적 스냅샷        │ ─────▶ │  외부 의존성 0             │
│    (web/index.html = 텍스트 + 그래프 내장)        │        │  즉시검색 · 클릭 탐색 (오프라인) │
└──────────────────────────────────────────────┘        └──────────────────────────┘
        ▲ 법 개정 반영은 이 단계만 주기적으로 재실행 (예: 월 1회)
```

- **데이터 수집은 배치**가 강제 — 폐쇄망이라 실시간 API 불가.
- **관계 계산은 AI 0%** — 위임·인용 모두 정규식 + 문맥 상태머신으로 도출. AI는 빌드 단계 감사용으로만.
- **런타임은 항상 즉각** — 스냅샷을 미리 구워두므로 클릭마다 재계산 없음.
- **빌드는 오픈API를 직접 호출** — korean-law MCP는 에이전트 세션에서만 접근 가능해 무인 재빌드에 쓸 수 없다.
  MCP는 탐색·검증용, 오픈API는 빌드용으로 역할을 나눈다.

## 실행

```bash
npm test               # 추출 규칙 · 신선도 · 검색 랭킹 회귀 (38케이스, 법제처 실원문 픽스처)
npm run collect        # 법제처 오픈API로 조달 핵심 30종 수집 → data/snapshot.json
npm run extract        # 관계 추출 통계 + 위임근거 커버리지 (검증용)
npm run build          # web/index.html 생성 (스냅샷+그래프 내장)
npm run smoke          # 산출물 검사 (외부 의존성 0 · 확인일 메타 · 문법)
```

수집에는 법제처 오픈API 자격증명이 필요합니다. `.env.example`을 `.env`로 복사해 `LAW_API_OC`를 채우세요
(신청: <https://open.law.go.kr>). 키 없이 `npm run build`를 돌리면 프로토타입 샘플로 빌드됩니다.

생성된 `web/index.html`은 더블클릭으로 열면 됨 — 서버·인터넷 불필요. (또는 `npm run serve`)

## 관계 추출 규칙 (`src/extract.mjs`, AI 없음)

관계를 3계층으로 나눠 **전부 규칙으로** 도출합니다. 근거는 [docs/scope.md §5.6](docs/scope.md).

**Layer 1 — 문서 위임** (법률 → 시행령 → 시행규칙)
`대통령령으로 정하는 바에 따라` / `○○부령으로 정한다` → 계열 하위법령.
실원문은 종결형(`정한다`)보다 **연결형**(`정하는 바에 따라`)이 훨씬 흔해 어미를 넓게 잡습니다.

**Layer 2 — 조문 인용** (왼→오 스캔, 문맥 `lastDoc` 유지)
- `「법명」 제N조의M` — 명시적 타법 인용 (스냅샷에 없으면 외부법 노드)
- `법 제N조` / `법률 제N조` — 상위 법률
- `영 제N조` / `시행령 제N조` — 계열 시행령
- `같은 법` / `같은 영` / `같은 조` — 직전 문맥 (상태머신)
- `제N조 내지 제M조`, `제N조부터 제M조까지` — 범위를 개별 조문으로 전개
- `제N조제M항제K호 가목` — 항·호·목은 엣지 근거에 기록 (노드는 조문 단위)
- **지역 별칭** — `「…시행령」(이하 "시행령"이라 한다)` 정의문을 읽어 문서별로 해석.
  이게 없으면 계약예규의 `시행령 제72조`를 해석할 수 없습니다.

**Layer 3 — 조문 → 행정규칙 위임** ★
`재정경제부장관이 정하는 심사기준`은 **대상이 텍스트에 없습니다.** 규칙으로는 "위임이 있었다"까지만 압니다.
대신 **행정규칙 제1조(목적)가 근거 조문을 밝힙니다**:

> 제1조(목적) 이 예규는 「국가를 당사자로 하는 계약에 관한 법률 시행령」…**제72조**에 의한 공동계약의 체결방법…

역방향으로 수집해 뒤집으면 정방향 위임 엣지가 완성됩니다. 이게 **법령 계층과 행정규칙 계층을 잇는 다리**이고,
없으면 그래프가 서로 닿지 않는 두 섬이 됩니다. 규칙이 못 잡은 잔여분은 `data/audit.json`에 감사 목록으로 남습니다.

## 검색 — 빠름은 이미 해결됐고, 문제는 랭킹이었다

실측(1,223조문 0.45MB): 단순 선형 스캔이 **타건당 2~3ms**. 속도는 병목이 아닙니다.
진짜 문제는 `수의계약`을 치면 **60건이 순위 없이 쏟아지는 것**이었습니다. 그래서 [search-runtime.js](src/search-runtime.js)의 핵심은 색인이 아니라 **랭킹**입니다.

| 매치 위치 | 점수 |
|---|---|
| 조문제목 정확 일치 | 700 |
| 조문제목 시작 / 초성 정확 | 450 / 500 |
| 조문제목 포함 / 초성 포함 | 300 / 380 |
| 소속 법령명 | 220 / 160 |
| 본문 (빈도 상한 있음) | 60~100 |
| + 법령 위계 | 법률 40 · 시행령 32 · 시행규칙 24 · 계약예규 16 |

조문제목과 법령명을 **분리해서** 색인합니다. 합치면 「예정가격작성기준」의 모든 조문이 상위를 점령해서 정작 국가계약법 제8조의2(예정가격의 작성)가 밀리기 때문입니다.

**지원하는 입력**
- 조번호 정규화 — `7조` = `제7조` = `제 7 조`, 가지조문 `제2조의2`
- 조번호 + 키워드 혼용 — `7조 보증금` → 공사계약일반조건 제7조(계약보증금)
- 초성 — `ㅅㅇㄱㅇ` → 수의계약, `ㅇㅈㄱㄱ` → 예정가격
- 띄어쓰기·구두점 무시

## 그래프 — 전역이 아니라 국소

전역 포스그래프는 실데이터에서 **동작하지 않습니다**. 1,354노드면 프레임당 916K 쌍 계산(60fps에 55M ops/sec)이라 브라우저가 기어갑니다. 그리고 1,354노드를 한 화면에 뿌리면 털뭉치라 정보가 0입니다.

그래서 **선택한 조문의 2홉 이웃(최대 48노드)만** 그립니다. 실무 질문은 "조달 법령 전체 지도"가 아니라 *"이 조문이 뭐랑 엮였나"*라서 이걸로 충분하고, 레이아웃이 잦아들면 애니메이션을 **정지**합니다(읽는 내내 CPU를 태우지 않도록).

## 법령 확인일 — 낡은 데이터를 최신인 것처럼 보이지 않게

폐쇄망 도구의 데이터는 **항상 과거**입니다. 가장 위험한 실패는 틀린 답이 아니라
**낡은 답을 최신인 것처럼 제시하는 것**입니다. 실무자가 근거로 쓰니까요.

섞으면 안 되는 두 가지를 분리합니다 (`src/freshness.mjs`):

| | 의미 | 판정 |
|---|---|---|
| **시행 상태** | 문서 자체의 성질 — 현행 / 시행예정 | 시행일 vs 기준일 비교로 **확정** |
| **확인 신선도** | 우리 스냅샷의 성질 — 확인일로부터 경과일 | 재수집 전에는 **알 수 없음** |

2026-07-21에 "현행"으로 확인한 조문이 08-01에 개정됐을 수 있습니다.
**"현행"은 단정이 아니라 확인일 시점의 주장**이므로 항상 경과일과 함께 보여줍니다.

**최신 데이터만 인용** — 법제처는 시행예정 개정본을 별도 MST로 함께 주므로 스냅샷에 섞일 수 있습니다.
- 시행예정본을 **가리키는** 인용·위임 엣지는 만들지 않습니다.
- 동명 법령이 현행/시행예정 둘 다 있으면 **항상 현행**을 고릅니다.
- 끊어낸 관계는 버리지 않고 `data/audit.json`의 `신선도차단`에 남깁니다.

**노출**
- 헤더: `기준일 · 현행 N건 · 시행예정 N건(인용 제외) · 최종확인 N일 전` (낡으면 주황색)
- 조문 상세: `시행 2026.06.03 · 확인 2026.07.21` 스탬프
- 빌드: 임계(기본 45일) 초과 시 경고. `--strict`면 실패, `--max-age N`으로 조정

```bash
npm run build -- --strict          # 낡은 법령 있으면 빌드 중단 (배포 전 게이트)
npm run build -- --max-age 30      # 임계를 30일로
npm run collect -- --refresh       # 캐시 무시하고 전량 재확인
```

## 로드맵

전체 범위와 근거는 [docs/scope.md](docs/scope.md) 참조.

1. **Phase 1** 조달 핵심 30종 (법령 13 + 계약예규 17) — 목표는 커버리지가 아니라 *추출 규칙 완성*. ← 현재
2. **Phase 2** 부처 교차 법령 26종 — 국토부·고용부·공정위 등 11개 부처. 인용되는 조문만 노드화하고 나머지는 스텁.
   산출물: `분리발주 3법` 뷰, `우선구매 경합` 뷰.
3. **Phase 3** 조달청 행정규칙 89~200종 — 볼륨 임계점(원문+색인 15~25MB).
   **Tauri 데스크톱 앱 전환 + 네이티브 색인 + 전역 핫키(Ctrl+Shift+Space).**
4. **Phase 4** 개정 추적 — 시행예정본 diff로 "이 조문 바뀌면 뭐가 영향받나" 임팩트 뷰.

kordoc 연동(HWP 계약서·공고 → 관련 조문 링크)은 Phase 3 이후. 로컬 파일 접근이 필요해 Tauri 전환이 선결입니다.
