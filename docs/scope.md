이 점프가 이 제품의 존재 이유다.

## 2.5 부처 교차 법령망 ★

조달청 업무는 조달 법령만으로 닫히지 않는다. **하나의 조문이 3개 부처로 뻗는다.**

### 증거: 국가계약법 시행령 제42조 (종합심사낙찰제 근거)

단일 조문 하나가 아래로 전부 뻗음 — 추정이 아니라 원문 확인:

```
국가계약법 시행령 제42조④
├─ 「국가유산수리 등에 관한 법률」 제2조제1호        → 국가유산청
├─ 「건설기술 진흥법」 제39조제2항                   → 국토교통부
├─ 「건설기술 진흥법 시행령」 제69조·제71조·제73조   → 국토교통부
├─ 「조달사업에 관한 법률 시행령」 제11조            → 조달청
└─ "재정경제부장관이 정하는 심사기준"               → 계약예규 종심제 심사기준
   그 아래 세부심사기준                             → 조달청 종심제 심사세부기준(51559)
```

⑤항의 계약이행능력심사는 다시 `하도급관리계획`·`외주근로자 근로조건 이행계획`을 심사요소로 명시 → **하도급법·근로 관계 법령**으로 연결.
④항의 `사회적 책임`은 종심제 심사기준에서 고용·안전·공정거래 항목으로 구체화 → **고용노동부·공정위**로 연결.

> 실무자가 "종심제 왜 이렇게 됐냐"를 추적하려면 **기재부 시행령 → 기재부 예규 → 조달청 세부기준 → 국토부/고용부/공정위 개별법**을 넘나들어야 함.
> 이 4단 점프가 현재 PDF 뒤지기로는 거의 불가능하고, **그래프가 실제로 값을 내는 지점**이다.

## 5. 엔지니어링 제약 (탐색 중 확인)

### 5.1 검색 API가 쿼리당 20건 하드캡
`search_admin_rule(display=100)` → 20건만 반환. `page` 파라미터 무시(동일 결과 재반환).
"조달청" 단일 쿼리는 가나다순 ㄱ~ㄷ 구간에서 잘림.

**영향**: 소관부처 기준 완전열거가 불가능. 키워드 파티셔닝으로 긁어모아야 하며 **완전성 보장 안 됨**.
→ 시드 목록(위 4장)을 `data/seed-admin-rules.json`으로 **수기 관리**하고, 빌드는 시드 기준으로 전문만 당겨오는 구조로 가야 함.
→ 누락 탐지는 별도 문제. 조달청 홈페이지 법령정보 목록과 주기적 대조 필요.

### 5.2 MCP는 빌드 파이프라인에서 호출 불가 ★
korean-law MCP는 **에이전트 세션에서만** 접근 가능. `src/build.mjs`가 직접 부를 수 없음.

선택지:
- **(A) 법제처 오픈API 직접 호출** — `build.mjs`가 OC 파라미터로 직접 호출. 무인 월간 재빌드 가능. **← 권장**
- (B) 에이전트가 MCP로 긁어 JSON 덤프 → 빌드는 그 JSON만 소비. 무인 자동화 불가(사람이 세션을 열어야 함).

MCP는 **탐색·검증용**, 오픈API는 **빌드용**으로 역할 분리하는 게 맞음.

### 5.3 추출 규칙의 구멍 (실데이터에서 확인)
`(계약예규) 공동계약운용요령` 원문에서 발견 — 현재 [extract.mjs](../src/extract.mjs)가 놓치는 패턴:

| 실제 표기 | 현재 규칙 | 상태 |
|---|---|---|
| `대통령령으로 정하는 바에 따라` | `~으로 정한다` | ❌ 연결형 누락 |
| `시행령 제72조` (이하 "시행령") | `영 제N조` | ❌ 표기 불일치 |
| `법률 제27조제1항제3호` | `법 제N조` | ❌ 표기 불일치 |
| `제72조제3항제2호` | `제N조` | ⚠️ 항·호 소실 |
| `제64조내지 제66조` | — | ❌ 범위 인용(`내지`) |
| `제2조의2` | — | ❌ 가지조문 |
| `계약예규 「공동계약운용요령」제11조` | — | ❌ 행정규칙→행정규칙 인용 |
| `[별첨1] 공동수급표준협정서` | — | ❌ 별표·서식 미처리 |
| `「건설기술 진흥법 시행령」제69조 … 같은 영 제71조` | `같은 법` | ❌ `같은 영` 미처리 |
| **`재정경제부장관이 정하는 심사기준`** | — | ❌ **법령→행정규칙 위임** |

**가장 중요한 누락은 마지막 줄이다.** 현재 위임 규칙은 `대통령령`/`기획재정부령`만 잡는데,
실제로 법령을 계약예규·조달청 고시로 잇는 다리는 **`○○장관이 정하는`** 패턴이다.
이걸 못 잡으면 법령 계층과 행정규칙 계층이 그래프에서 **완전히 분리된 두 섬**이 된다.
변형: `~장관이 정하는`, `~장관이 정하여 고시하는`, `조달청장이 정하는`, `각 중앙관서의 장이 정한다`.

**긍정 신호**: 계약예규가 상위 법령을 조문 단위로 촘촘히 인용함 → 위임·인용 그래프의 **가장 값진 엣지가 여기서 나옴**.
법률↔시행령 위임은 이미 알려진 관계지만, "이 예규 조항의 근거가 시행령 몇 조인가"는 실무자가 실제로 헤매는 지점.

### 5.4 볼륨 → 단일 HTML 한계
`공동계약운용요령` 1건이 본문+부칙+별첨3종 = **약 15KB**. 중간 크기 예규 기준.

| 항목 | 추정 |
|---|---|
| 문서 수 | 190~300 |
| 조문 노드 | 10,000~18,000 |
| 원문 텍스트 | **6~10MB** |
| + 역색인 | **15~25MB** |

부처 교차 법령(§2.5)에 산업안전보건법·건설산업기본법·공정거래법 같은 **대형 법률**이 다수 포함되어
1차 추정(3~5MB)보다 2배가량 커졌다. 현재 `web/index.html`은 24KB(샘플 21노드) — 실데이터는 **600~1,000배**.
→ 자족형 단일 HTML 원칙(AGENTS.md 불변원칙 1)이 물리적으로 깨짐. Tauri 전환 + 네이티브 색인이 정당화되는 지점.

### 5.6 관계 추출: 규칙기반으로 되는가? → **된다. AI 불필요** ★

관계를 3계층으로 분해하면 각각 난이도가 다르다.

#### Layer 1 — 문서 단위 위임 (법률 → 시행령 → 시행규칙)
법제처에 **법령체계도 API**(`get_law_system_tree`)가 실재. 상위법·하위법·관련법령·행정규칙을 구조화 데이터로 반환.

⚠️ **단, 불완전하다 (실측)**:
- 국가계약법 체계도의 행정규칙 16건 중 **계약예규는 4종뿐** (공사입찰유의서·물품구매계약일반조건·예정가격작성기준·정부입찰계약집행기준).
  적격심사기준·공동계약운용요령·협상에의한계약체결기준·공사계약일반조건 등 **13종 누락**.
- 조달청 훈령/고시는 거의 미포함.
- 법률(283877)과 시행령(285893)을 각각 조회해도 **동일 결과** 반환 → 문서별이 아닌 법령군 단위의 거친 데이터.

→ **뼈대로만 쓰고 신뢰하지 말 것.** 실제로는 법령명 문자열 규칙(`"X법 시행령"의 상위는 "X법"`)이 더 정확하고 100% 도출 가능.

#### Layer 2 — 조문 단위 인용 (`「법명」 제N조`)
원문에 **명시적으로 박혀 있음**. 정규식으로 완결. AI 0%.
§5.3의 패턴 구멍만 메우면 됨. 이미 실데이터로 검증 완료.

#### Layer 3 — 조문 단위 위임 (`재정경제부장관이 정하는 심사기준` → 어느 예규 몇 조?)
정방향 텍스트에는 **대상이 안 적혀 있다.** 규칙으로는 "위임이 발생했다"까지만 알 수 있음.
→ 언뜻 AI가 필요해 보이는 지점. **하지만 역방향 단서가 있다.**

**계약예규 제1조(목적)가 근거 조문을 명시한다** — 2/2 실측 확인:

| 예규 | 제1조 원문 | 도출되는 엣지 |
|---|---|---|
| 공동계약운용요령 | "「국가계약법 시행령」…**제72조**에 의한 공동계약의 체결방법…" | 시행령 제72조 →위임→ 공동계약운용요령 |
| 종합계약집행요령 | "「국가계약법 시행령」…**제71조**에 의한 종합계약의 체결방법…" | 시행령 제71조 →위임→ 종합계약집행요령 |

이건 우연이 아니라 **법제 입안 관행**(훈령·예규 제1조에 위임근거 명시)이라 광범위하게 성립한다.

→ **역방향으로 수집해서 뒤집으면 정방향 위임 엣지가 완성된다. 규칙기반으로 가능.**

#### 결론 및 AI의 자리

| Layer | 방법 | AI |
|---|---|---|
| 문서 위임 | 법령명 문자열 규칙 + 체계도 API 교차검증 | 0% |
| 조문 인용 | 정규식 (§5.3 패턴 보강) | 0% |
| 조문 위임 | **예규 제1조 역방향 파싱 → 반전** | 0% |
| 잔여 미매칭 | 커버리지 감사 | 보조만 |

**AGENTS.md 불변원칙 2(런타임 AI 금지)는 유지 가능하다.** 관계망 자체는 규칙으로 나온다.

AI를 쓴다면 **빌드 단계의 감사 도구로만**:
- 규칙이 못 잡은 잔여 위임(`○○장관이 정하는`인데 대응 예규를 못 찾은 건)을 목록으로 뽑기
- 사람이 확인 → `data/seed-*.json`에 수기 기록 → 이후 빌드는 다시 순수 규칙

**AI 출력을 그래프에 직접 넣지 말 것.** 법령은 오답 비용이 크고, "AI가 추론한 관계"는 실무자가 근거로 쓸 수 없다.
규칙기반 엣지는 원문 문자열을 근거로 제시할 수 있다는 점이 결정적 차이다.

### 5.5 부칙·시행예정·연혁
- 모든 문서에 부칙이 붙어 있고 개정이력이 조문 내 `<개정 2020.12.28.>` 인라인으로 박혀 있음 → 개정추적 뷰의 원재료로 바로 쓸 수 있음.
- 조달사업법 등 **시행예정 개정본**이 별도 MST로 존재 → "현행 vs 시행예정" 토글이 실무 가치 큼.

## 6. 우선순위 제안

**Phase 1 — 조달 핵심 30종** (법령 13 + 계약예규 17)
조문 ~1,500, ~1MB. 단일 HTML로도 아직 감당 가능.
목표는 커버리지가 아니라 **추출 규칙 완성**(§5.3) — 특히 `○○장관이 정하는` 위임을 잡아
법령↔행정규칙 두 계층을 하나의 그래프로 잇는 것. 여기서 실패하면 뒤가 다 무의미.

**Phase 2 — 부처 교차 법령 26종** (§2.5)
타부처 법령은 **전문을 다 담을 필요가 없다.** 실제 인용되는 조문(예: 건설기술 진흥법 제39조②,
시행령 제69·71·73조)만 노드화하고 나머지는 스텁 처리 → 볼륨을 1/5로 억제.
`분리발주 3법`과 `우선구매 경합` 두 뷰가 여기서 나옴 — 실무 체감이 가장 큰 산출물.

**Phase 3 — 조달청 행정규칙 89~200종**
볼륨이 터지는 지점. **Tauri + 네이티브 색인 전환 시점.**

**Phase 4 — 개정추적**
시행예정본 diff. 조달사업법·산업안전보건법 등 이미 시행예정 MST가 다수 확보되어 있음.
