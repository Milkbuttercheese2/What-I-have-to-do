# 별표 첨부파일(PDF·HWP) 실측 조사 — "원문은 뷰어로, 검색은 파싱으로"

> 조사일 2026-07-22 · 브랜치 `phase1-real-data` · 전부 실측(투영치는 표본에서 산출, 계산식 명시)
> 받은 파일은 프로젝트 밖 스크래치패드에만 두었다. `src/` `test/` `web/` `data/` 는 건드리지 않았다.

## 결론 3줄

1. **뷰어는 된다.** 다운로드는 인증 없이 100% 성공(466/466, 리다이렉트 0), `file://` 에서
   `<iframe src="./annex/x.pdf">` 에 크롬 **내장 PDF 뷰어가 실제로 붙고 표까지 렌더된다**(스크린샷 확인).
   PDF 217/217에 텍스트층이 있어 뷰어 안에서 Ctrl+F 도 된다. HWP 는 브라우저가 못 연다 — 내려받기 전용이 맞다.
2. **막는 건 크기다.** 1,869건 전량 동봉 = **PDF 143MB + HWP 57MB ≈ 200MB**(gzip 해도 160MB, data-URI 면 266MB).
   지금 `web/index.html` 28.67MB 의 **7~9배**. 단일 HTML 노선은 여기서 끝난다. 폴더 동봉(c)이 유일하게 현실적이다.
3. **파일 동봉과 무관하게 지금 당장 이득인 게 하나 있다** — kordoc **CLI**(MCP 아님, 빌드에서 호출 가능)로 뽑은
   텍스트가 현재 罫線 복원본보다 품질이 높으면서 **크기는 0.415배**다. 별표 텍스트 13.52MB → 5.61MB,
   산출물 28.67MB → **약 20.8MB**. 현재 罫線 표의 **60%(977/1,629)는 애초에 화면에 표로 그려지지도 않는다.**

## 1. 다운로드 — 되는가

표본: 별표 보유 문서 223건 중 **24건**(등간격 추출)의 원시 API 응답 → **별표단위 217건**(전체 1,869건의 11.6%).
그 217건의 HWP·PDF·이미지 링크를 **전부 실제로 내려받았다(466개 파일)**.

| 항목 | 실측 |
|---|---|
| `별표서식파일링크`(HWP) 보유 | **217/217 (100%)** |
| `별표서식PDF파일링크` 보유 | **217/217 (100%)** |
| `별표서식이미지파일링크` 보유 | 20/217 (9.2%) — 파일 32개(GIF) |
| HTTP 상태 | **전부 200**, 리다이렉트 **0건** |
| OC(인증) 파라미터 | **불필요** — OC 없이 `https://www.law.go.kr/LSW/flDownload.do?flSeq=…` 로 바로 받힘 |
| Content-Type | `application/hwp`(HWP5·OLE) 112 · `application/hwp+zip`(HWPX) 105 · `application/pdf` 217 · `image/gif` 32 |
| Content-Length | **안 옴**(chunked) — HEAD 는 404. 크기를 미리 알려면 실제로 받아야 한다 |
| Content-Disposition | URL 인코딩된 원본 파일명. 디코드하면 `[별표 2] 부정당업자의 입찰참가자격 제한기준(제76조 관련)(국가를 당사자로 하는 계약에 관한 법률 시행규칙).pdf` |
| 요청 소요 | 평균 **38ms/건**(동시 5) |

- HWP 는 **두 포맷이 섞여 온다**: HWP5 바이너리 112건(52%), HWPX(zip) 105건(48%). 확장자는 둘 다 `.hwp` 로 오지만
  Content-Disposition 파일명은 `.hwpx` 로 온다. 저장할 때 이름을 그대로 쓰면 문제 없다.
- 캐시(`.cache/*.json`)는 **정규화 결과**를 담고 있어 링크가 없다. 링크를 스냅샷에 넣으려면 `--refresh` 가 필요하다(기지 사실).

## 3. 오프라인에서 볼 수 있는가 — 실측

크롬 150 헤드리스 + CDP 로 `file://` 페이지를 직접 띄워 확인했다.

| 방식 | 결과 | 근거 |
|---|---|---|
| `<iframe src="./annex/x.pdf">` | **된다** | 프레임 트리에 `file://…pdf` 로 이동 확인. 브라우저 타깃 목록에 `chrome-extension://mhjfbmdgcfjbbpaeojofohoefgiehjai/index.html`(크롬 내장 PDF 뷰어) **iframe 3개** 생성 |
| `<embed type="application/pdf">` | **된다** | 위와 동일(3개 중 1개) |
| `<object data="…pdf">` | **된다** | 위와 동일 |
| PDF 실제 렌더 | **된다** | `Page.captureScreenshot` 으로 별표6 세부평가기준 표가 그대로 그려진 것 확인 |
| PDF 안에서 Ctrl+F | **된다** | 표본 PDF **217/217 텍스트층 보유, OCR 필요 0건**(kordoc `NEEDS_OCR` 경고 0) |
| `navigator.pdfViewerEnabled` | `true` | 플러그인 목록에 PDF Viewer 5종 |
| `.hwp` 링크 클릭 | **내려받기만** | `Page.navigate` 결과 `isDownload:true`, `Page.downloadWillBegin` 발생, 69,632B 수신. 표시 불가 확정 |
| `fetch('file://…')` | **차단** | `Cross origin requests are only supported for protocol schemes: chrome, …, data, http, https`. 즉 런타임에 로컬 파일을 읽어 blob 을 만드는 경로는 없다 |
| `data:application/pdf;base64,…` iframe | **된다** | 인라인 base64 로 넣으면 내장 뷰어가 붙는다(옵션 b 는 기술적으로는 성립) |
| `blob:` iframe | **된다** | 단, 원본을 fetch 로 못 읽으니 결국 인라인 base64 가 전제 |

**⚠ 실측된 함정 하나.** `annex/` 폴더가 빠진 채 `index.html` 만 복사돼도 **페이지는 그걸 감지하지 못한다.**
없는 파일을 가리킨 iframe 은 `error` 가 아니라 **`load` 이벤트가 뜨고** `contentDocument` 는 정상 케이스와 똑같이 `null` 이다.
"낡음/결손은 항상 눈에 보여야 한다"(AGENTS.md 원칙 6)에 정면으로 걸린다 — 폴더 동봉을 택한다면
**목록·건수·체크섬을 인라인으로 넣고 화면에 '부록 폴더 없음'을 표시할 다른 수단**이 필요하다(자동 감지는 불가).

## 4. kordoc 로 파싱 — 검색용 텍스트 품질

**중요: kordoc 은 MCP 전용이 아니다.** `npx kordoc <files…> -d <dir> --format markdown|json|chunks` 라는
**CLI 가 있다** → 무인 월간 재빌드에서 그대로 쓸 수 있다(AGENTS.md "MCP는 빌드에 못 쓴다" 제약을 우회).

처리량 실측(표본 217건 일괄):

| | 소요 | 건당 | 1,869건 투영 |
|---|---:|---:|---:|
| HWP → markdown | 6.1초 | 28ms | **약 1분** |
| PDF → markdown | 22.2초 | 102ms | **약 3분** |

### 품질 비교 (표본 217건, 현재 `tidyAnnexText`+`AnnexTable` 대비)

| 항목 | 현재(罫線 텍스트) | kordoc |
|---|---|---|
| 표 구조 | 罫線 문자열. 렌더 시 `AnnexTable` 이 `┌┬┐├┼┤└┴┘│` 만 인식 | `<table>` + **rowspan/colspan/중첩표** 복원 |
| 罫線 보유 별표가 실제로 표로 그려지는 비율 | **652/1,629 = 40%** — 나머지 **977건(60%)은 罫線 그대로 노출** | 176/217이 표 구조 산출 |
| 굵은 罫線(`┏━┓┣╋┫┃`) | `BORDER`/`ROW` 정규식이 모름 → 표로 안 그려짐 | 정상 처리 |
| 개정일 | **소실**. `clean()` 이 `<개정 2025. 5. 1.>` 을 HTML 태그로 보고 지운다 — 전체 1,869건 중 본문에 개정 연도가 남은 건 **0건** | `<개정 2025. 5. 1.>` 보존 |
| 문자 깨짐 | 가운뎃점이 `?` 로 (`4?5급`, `서기관 ? 과학기술서기관`) — **286건 의심** | `4·5급` 로 복원 |
| 줄바꿈 | 고정폭 절단 유지(단어 중간 절단 751곳/58,020줄=1.3%) — 의도된 설계지만 스니펫 표시에는 불리 | 문장 단위로 이어짐 |
| 문자 수 | 기준 1.00 | **0.462** (罫線·패딩 공백이 사라져서) |
| 바이트 (스냅샷 텍스트 대비) | 기준 1.00 | **0.415** |
| 실패 | — | 14/217(6.5%)이 거의 빈 결과 → **확인해 보니 전부 "삭제" 처리된 서식**이라 손실 아님. 나머지 40건의 문자 감소는 서식의 빈 칸 패딩 소실 |
| PDF 파싱 | — | HWP 와 문자량 사실상 동일(0.462), 다만 셀 병합이 HWP보다 거칠다(`최근2년 이내 최근3년 이내` 합쳐짐) → **HWP 우선, PDF는 폴백** |

**⇒ 검색 색인용으로 kordoc 이 현재 방식보다 낫다.** 게다가 별표 텍스트를 kordoc 마크다운으로 갈아끼우면
**13.52MB → 5.61MB**, 산출물 **28.67MB → 약 20.8MB**(−7.9MB). 파일 동봉 여부와 독립된 이득이다.

### 판단에 필요한 사실 정리 (결정은 사용자 몫)

- 단일 HTML 을 지키려면 파일 동봉은 불가능하다. (b)는 295MB로 배포·로딩 양쪽에서 비현실적이다.
- 파일을 보여주려면 (c)/(d) = 폴더 배포이고, 그건 **불변원칙 1의 "형태는 바뀐다"** 조항이 예고한 Phase 3 전환과 같은 방향이다.
  AGENTS.md 가 적은 Tauri 트리거는 15~25MB인데 현재 산출물 28.67MB로 **이미 넘었다**. 부록 200MB는 트리거를 8배로 넘긴다.
- Tauri 로 가면 200MB 리소스는 앱 번들·별도 데이터 디렉터리로 다룰 수 있고, HWP 는 OS 쉘로 한글에 넘길 수 있으며,
  `file://` 의 fetch 차단·결손 미감지 문제도 사라진다. 즉 **"뷰어로 보여준다"는 요구는 Tauri 전환과 사실상 한 묶음이다.**
- 반대로 **(e)는 지금 브랜치에서 바로 할 수 있다.** 산출물을 8MB 줄이면서 검색 품질도 올린다. 파일 동봉을 나중에 (c)로
  확장할 때 텍스트 파이프라인은 그대로 재사용된다 — 선택지를 닫지 않는다.
