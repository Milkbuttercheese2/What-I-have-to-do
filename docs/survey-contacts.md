# 소관부처·담당부서·담당자 연락처 조사 (2026-07-22)

> 조사 대상: 법제처 국가법령정보 오픈API (`lawService.do` / `lawSearch.do`) · korean-law MCP
> 표본: 법령 25종(seed 13 전수 + 부처 교차 12종) · 행정규칙 **307종 전수**(snapshot 수록분 전부)
> 방법: 실제 API 호출 후 `기본정보`/`행정규칙기본정보` 필드 존재 여부 집계. 추정 없음.

## 결론 3줄

1. **소관부처·담당부서·부서 전화번호는 전부 온다 — 법령 25/25(100%), 행정규칙 307/307(100%).**
   추가 호출 없이 지금 받고 있는 본문 응답(`lawService.do`) 안에 이미 들어 있다. 쓰지 않고 버리는 중이다.
2. **담당자 "이름"은 행정규칙만 온다(300/307, 97.7%). 법령은 0/25 — 이름 필드 자체가 없다.**
   대신 법령은 `연락부서.부서단위[]` 로 **부서별 전화번호를 복수** 준다(25종에 53개 부서단위).
   개인 직통번호·이메일·직위는 **어느 쪽에서도 오지 않는다.** 오는 것은 부서 대표번호다.
3. **korean-law MCP 는 이 정보를 하나도 주지 않는다** — 소관부처/담당자 관련 도구가 없고,
   `search_law`·`get_admin_rule` 응답 헤더에서 해당 필드를 버린다. 이 건은 오픈API가 유일한 경로다.

### 1.1 `부서단위` 는 배열이 아닐 수 있다 — 구현 함정

**단일 부서면 객체, 복수면 배열로 온다.** (실측)

```jsonc
// 복수 (국가계약법)
"연락부서": { "부서단위": [
  { "부서명": "계약정책과",           "부서연락처": "044-215-5211, 5217, 5218", "소관부처명": "재정경제부" },
  { "부서명": "규제개혁법무담당관실", "부서연락처": "042-724-7277, 7249",       "소관부처명": "조달청"    }
]}
// 단일 (특정물품 특례규정)
"연락부서": { "부서단위":
  { "부서명": "계약정책과", "부서연락처": "044-215-5213, 5217, 5218", "소관부처명": "재정경제부" }
}
```
→ `lawapi.mjs` 의 기존 `asArray()` 를 반드시 통과시킬 것.

### 1.2 부서명에 **소관 범위가 조문 단위로 적혀 있다** — 예상 밖의 수확

부처 교차 법령에서 부서명이 단순 부서명이 아니라 `부서 - 담당범위(조문)` 형태로 온다:

| 법령 | 부서단위 수 | `부서명` 실측값 |
|---|---|---|
| 중소기업제품 구매촉진 및 판로지원에 관한 법률 | 5 | `판로정책과 - 우선조달(제4조)` / `판로정책과 - 직접생산(제9조~제11조)` / `판로정책과 - 경쟁제품, 공사용자재 등(제6조~제8조의3, 제12조)` … |
| 건설산업기본법 | 4 | `건설정책과-건설업등록관리, 제재처분` / `공정건설지원과-하도급` / `건설정책과-보증, 실적신고` |
| 하도급거래 공정화에 관한 법률 | 5 | `기업거래정책과-표준하도급계약서` / `기업거래정책과-기술유용제도` |
| 국가재정법 | 5 | `기획예산처>지출혁신과` + `재정경제부>국고총괄과(국가보증채무)` 등 **부처가 섞임** |
| 민법 | 1 | `법무심의관실` |

**Phase 2(부처 교차 26종)에서 "이 조문은 어디에 전화하나"를 조문 단위로 안내할 수 있다는 뜻이다.**
다만 형식이 `-`/` - `/`(…)` 로 제각각이라 **파싱해서 구조화하지 말고 문자열 그대로 노출**할 것을 권한다.
(조달 핵심 13종은 전부 부서명만 오고 범위 표기가 없다 — 파싱해도 이득이 없다.)

## 4. korean-law MCP — 이 목적으로는 쓸모 없음

- `discover_tools("소관부처 담당부서 담당자 연락처")` → **0건.** 32개 카테고리 어디에도 해당 도구 없음.
- `discover_tools("법령조회")` → `get_law_text` / `get_article_detail` / `get_batch_articles` /
  `get_article_with_precedents` — 넷 다 조문 본문만.
- `search_law("국가를 당사자로 하는 계약에 관한 법률")` 응답: 법령ID·MST·공포일·시행일·구분.
  **원본 목록 API에는 있는 `소관부처명` 을 MCP가 포맷 단계에서 버린다.**
- `get_admin_rule(id=2100000276688)` 응답 헤더: `행정규칙명` / `종류` 두 줄뿐.
  **원본에 있는 소관부처·담당부서·담당자·전화가 전부 사라진다.**

결론: MCP는 오픈API의 **부분집합**이다. 이 건에서 MCP를 볼 이유가 없다.
(AGENTS.md §4 "MCP는 탐색·검증용" 원칙과도 일치 — 빌드는 오픈API 직접 호출이 맞다.)

## 6. `snapshot.json` 구조 제안

`verification` 은 **"언제 확인했고 얼마나 낡았나"** 를 담는 자리다(원칙 6).
소관부처·연락처는 성격이 다르다 — 낡음 판정이 아니라 **문서의 귀속 정보**다.
그래서 `verification` 에 섞지 말고 형제 필드 `authority` 로 분리할 것을 제안한다.

```jsonc
{
  "id": "nca",
  "name": "국가를 당사자로 하는 계약에 관한 법률",
  "docType": "법률",
  "source": { "kind": "law", "mst": "283877", "lawId": "000695" },

  // 새로 추가 — 문서의 귀속·연락 정보
  "authority": {
    "부처": "재정경제부",           // law: 소관부처.content / admrul: 상위부처명(§2.1)
    "부처코드": "1053000",
    "담당자": null,                 // admrul만 채워진다. law는 항상 null
    "부서": [                       // 항상 배열로 정규화 (law의 객체/배열 흔들림 흡수)
      { "부처": "재정경제부", "부처코드": "1053000", "부서명": "계약정책과",           "연락처": "044-215-5211, 5217, 5218" },
      { "부처": "조달청",     "부처코드": "1230000", "부서명": "규제개혁법무담당관실", "연락처": "042-724-7277, 7249" }
    ]
  },

  // 기존 — 신선도만. 여기에 시행일/효력을 admrul에도 채운다(§5)
  "verification": {
    "확인일": "2026-07-21T21:51:11.290Z",
```

### 구현 시 주의 4가지

1. **`findKey()` 를 쓰지 말고 명시 경로로 읽을 것.** `lawapi.mjs` 의 `findKey` 는 DFS 재귀 탐색이라
   법령 응답에서 `소관부처명` 을 찾으면 `부서단위[]` 안쪽 값이 먼저 잡힐 수 있다(부처가 다른 경우 오답).
   `json.법령.기본정보.소관부처.content` 처럼 못 박아 읽어라.
2. **`연락부서.부서단위` 는 객체일 수 있다** — `asArray()` 필수 (§1.1).
3. **`소관부처명` 대신 `상위부처명`** (행정규칙, §2.1). 8건이 부서명으로 오염돼 있다.
4. **담당자 실명이 산출물에 박힌다.** 300명분 공무원 실명이 `web/index.html` 에 들어가고 폐쇄망에 배포된다.
   법제처가 공개하는 정보이긴 하나, 이름은 부서보다 훨씬 빨리 낡는다(인사이동).
   → **UI 기본 표기는 `부처 · 부서 · 전화`, 담당자명은 접어두거나 옵션 처리**를 권한다.
   확인일이 6개월 지난 담당자명은 사실상 오정보다.
